f:T1f611,<p>Training a Medusa head only teaches it to propose future tokens. It does not make those proposals final output. At runtime, the original target model must still verify them.</p>
<p>This is the second of two articles. <a href="/blog/medusa-multi-token-prediction/">Part I: Architecture, Training, and Shifted Loss</a> develops the heads and their loss. This article begins exactly where training ends.</p>
<p>Every inference iteration follows four decisions:</p>
<ol>
<li>The original LM head selects a root token.</li>
<li>Every Medusa head supplies a top-K pool for its future position.</li>
<li>A fixed sparse rank tree determines which combinations are worth verifying.</li>
<li>Target-model logits and the selected acceptance rule determine which prefix is committed.</li>
</ol>
<p>The distinction to keep throughout the article is:</p>
<blockquote>
<p>Top-K selection decides what Medusa proposes. Greedy, rejection-sampling, or typical acceptance decides what the target allows into the output.</p>
</blockquote>
<h2>Part 1: One Medusa Inference Iteration, Without Skipping Steps</h2>
<p>Consider a prompt ending with:</p>
<p>The cat</p>
<p>Assume the current final hidden state is <span class="katex"><span class="katex-mathml"><math xmlns="http://www.w3.org/1998/Math/MathML"><semantics><mrow><msub><mi>h</mi><mi>t</mi></msub></mrow><annotation encoding="application/x-tex">h_t</annotation></semantics></math></span><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.8444em;vertical-align:-0.15em;"></span><span class="mord"><span class="mord mathnormal">h</span><span class="msupsub"><span class="vlist-t vlist-t2"><span class="vlist-r"><span class="vlist" style="height:0.2806em;"><span style="top:-2.55em;margin-left:0em;margin-right:0.05em;"><span class="pstrut" style="height:2.7em;"></span><span class="sizing reset-size6 size3 mtight"><span class="mord mathnormal mtight">t</span></span></span></span><span class="vlist-s">​</span></span><span class="vlist-r"><span class="vlist" style="height:0.15em;"><span></span></span></span></span></span></span></span></span></span>. One forward pass produces:</p>
<pre><code class="language-text">Original LM head, top-1:  sat

Medusa head 0, top-2:    on, slept
Medusa head 1, top-2:    the, .
</code></pre>
<p>The original head predicts the root token sat. The two Medusa heads independently predict the next two positions after that root.</p>
<p>The complete candidates are:</p>
<pre><code class="language-text">sat on    the
sat on    .
sat slept the
sat slept .
</code></pre>
<p><img src="/assets/img/medusa-candidate-tree.svg" alt="Two-level Medusa candidate tree with two retained ranks at each level"></p>
<p>The implementation does not duplicate the prompt four times and run four ordinary target batches. It flattens the shared nodes into one tree and applies a special attention mask so each node sees only its own ancestors.</p>
<p>Suppose target verification says:</p>
<pre><code class="language-text">After "The cat"         target wants "sat"
After "The cat sat"     target wants "on"
After "The cat sat on"  target wants "the"
</code></pre>
<p>Then the path</p>
<p>sat on the</p>
<p>matches for its entire represented depth. One verification iteration commits three tokens:</p>
<pre><code class="language-text">root target token:       sat
accepted Medusa token 1: on
accepted Medusa token 2: the
</code></pre>
<p>The next iteration begins from the new prefix:</p>
<p>The cat sat on the</p>
<p>The selected verification node supplies the new final state and head logits. Those outputs produce new top-K lists, the same fixed tree topology is filled with new token IDs, and verification repeats.</p>
<p>If instead the target wanted slept after sat, the sat on ... paths would fail immediately. If one of the retained head-0 ranks contains slept, a path beginning with that rank can still win. If no retained rank matches, Medusa commits only sat and starts the next iteration.</p>
<p>This is the entire runtime loop:</p>
<pre><code class="language-text">prefill prompt
-> produce root and head distributions
-> fill candidate tree
-> verify tree with target backbone
-> choose longest accepted prefix
-> copy only selected KV-cache states
-> repeat from committed prefix
</code></pre>
<p>The draft heads do not recursively rerun while creating this tree. They generate their distributions from one backbone state. The target backbone is then run for tree verification. After the initial prompt prefill, that verification pass also supplies the selected base and Medusa logits needed to construct the next tree; there is no extra standalone prompt pass between decode iterations.</p>

<h2>Part 3: How Medusa Chooses an Optimized Sparse Tree</h2>
<p>The optimized tree is chosen offline, not separately for every prompt.</p>

<p>It estimates how often that rank combination will correctly extend the accepted prefix to that depth.</p>
<h3>Step 3: grow a prefix-closed tree under a budget</h3>
<p>Begin with the root. Repeatedly add the highest-scoring node whose parent is already present. Stop when the node budget is exhausted.</p>
<p>A toy calibration makes the behavior clear:</p>
<p>head 0: rank 0 = 0.60, rank 1 = 0.20
head 1: rank 0 = 0.50, rank 1 = 0.10</p>
<p>The candidate node scores include:</p>
<p>(0,)   = 0.60
(1,)   = 0.20
(0,0)  = 0.60 x 0.50 = 0.30
(0,1)  = 0.60 x 0.10 = 0.06
(1,0)  = 0.20 x 0.50 = 0.10</p>
<p>The greedy order can begin:</p>
<p>(0,) -> (0,0) -> (1,) -> (1,0) -> (0,1)</p>
<p>The search goes deeper under a reliable top-ranked prefix before spending many nodes on unlikely branches. This produces the characteristic left-heavy tree.</p>
<p>For a prefix-closed tree <span class="katex"><span class="katex-mathml"><math xmlns="http://www.w3.org/1998/Math/MathML"><semantics><mrow><mi>T</mi></mrow><annotation encoding="application/x-tex">T</annotation></semantics></math></span><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6833em;"></span><span class="mord mathnormal" style="margin-right:0.1389em;">T</span></span></span></span>, the paper approximates expected accepted length as</p>
<span class="katex-display"><span class="katex"><span class="katex-mathml"><math xmlns="http://www.w3.org/1998/Math/MathML" display="block"><semantics><mrow><mi mathvariant="double-struck">E</mi><mo stretchy="false">[</mo><mi>L</mi><mo stretchy="false">]</mo><mo>≈</mo><munder><mo>∑</mo><mrow><mi>u</mi><mo>∈</mo><mi>T</mi></mrow></munder><mi mathvariant="normal">score</mi><mo>⁡</mo><mo stretchy="false">(</mo><mi>u</mi><mo stretchy="false">)</mo><mi mathvariant="normal">.</mi></mrow><annotation encoding="application/x-tex">\mathbb{E}[L]
\approx
\sum_{u\in T}\operatorname{score}(u).</annotation></semantics></math></span><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:1em;vertical-align:-0.25em;"></span><span class="mord mathbb">E</span><span class="mopen">[</span><span class="mord mathnormal">L</span><span class="mclose">]</span><span class="mspace" style="margin-right:0.2778em;"></span><span class="mrel">≈</span><span class="mspace" style="margin-right:0.2778em;"></span></span><span class="base"><span class="strut" style="height:2.3717em;vertical-align:-1.3217em;"></span><span class="mop op-limits"><span class="vlist-t vlist-t2"><span class="vlist-r"><span class="vlist" style="height:1.05em;"><span style="top:-1.8557em;margin-left:0em;"><span class="pstrut" style="height:3.05em;"></span><span class="sizing reset-size6 size3 mtight"><span class="mord mtight"><span class="mord mathnormal mtight">u</span><span class="mrel mtight">∈</span><span class="mord mathnormal mtight" style="margin-right:0.1389em;">T</span></span></span></span><span style="top:-3.05em;"><span class="pstrut" style="height:3.05em;"></span><span><span class="mop op-symbol large-op">∑</span></span></span></span><span class="vlist-s">​</span></span><span class="vlist-r"><span class="vlist" style="height:1.3217em;"><span></span></span></span></span></span><span class="mspace" style="margin-right:0.1667em;"></span><span class="mop"><span class="mord mathrm">score</span></span><span class="mopen">(</span><span class="mord mathnormal">u</span><span class="mclose">)</span><span class="mord">.</span></span></span></span></span>
<p>The optimization is therefore:</p>
<ul>
<li>maximize estimated accepted length,</li>
<li>subject to a fixed node budget,</li>
<li>and the rule that a node's parent must already exist.</li>
</ul>
<p>The Medusa paper reports using AlpacaEval statistics to shape the sparse Vicuna-7B tree. It separately benchmarks tree sizes because a larger tree raises acceptance but also increases linear-layer and attention work. In its ablation, a sparse 64-node tree outperformed dense settings with 256 nodes. The optimum is a model-dataset-hardware property, not a universal constant.</p>

head 2 ranks: 0=" a",   1=" on",  2=" very",  ...
</code></pre>
<p>The static tuple</p>
<p>(0, 2, 1)</p>
<p>is instantiated as</p>
<p>"The" + " cat" + " sat" + " on"</p>
<p>On the next iteration, (0, 2, 1) remains in the topology but maps to completely different token IDs because the head distributions changed.</p>
<p>This separates the two selection problems:</p>
<table>
<thead>
<tr>
<th>Decision</th>
<th>When?</th>
<th>What decides it?</th>
</tr>
</thead>
<tbody>
<tr>

<td>Calibration accuracies plus a node budget</td>
</tr>
<tr>

</tr>
<tr>

<p>The offline score never overrides the target model at runtime. It only decides which proposals are worth presenting to the target.</p>
<h2>Part 6: Tree Attention Verifies Shared Prefixes Once</h2>
<p>If we expanded every leaf into a separate batch row, shared prefixes would be duplicated. Tree attention represents each distinct node once.</p>
<p>For the official Vicuna tree, the principal tensors are conceptually:</p>
<pre><code class="language-text">tree_candidates:      [1, 64]
tree attention mask:  [1, 1, 64, 64]
tree position IDs:    [64]
retrieved paths:      [42, 5]
verifier logits:      [42, 5, vocabulary]
</code></pre>
<p>The exact dimensions can acquire singleton axes inside the implementation, but the semantics are stable.</p>
<p>The attention mask grants a node access to:</p>
<ul>
<li>every original prompt token,</li>
<li>the root candidate,</li>
<li>only the candidate nodes on its own ancestor path.</li>
</ul>
<p>It cannot attend to siblings or tokens from another continuation. Position IDs are assigned by tree depth, so two siblings occupy the same logical sequence position even though they have different flattened indices.</p>
<p>After the target forward pass, retrieval indices reconstruct 42 padded root-to-leaf paths from the 64 node outputs. Only KV-cache entries belonging to the selected accepted path are copied into the contiguous decode cache. The other verified branches are discarded.</p>
<p>This is why production Medusa is neither:</p>
<p>four prompts copied into a normal batch</p>
<p>nor:</p>
<p>four separate target-model forward passes.</p>
<p>It is one tree-shaped target pass with shared prefix nodes and a custom causal mask.</p>
<h2>Part 7: Exact Greedy Verification and Rejection</h2>
<p>Let</p>
<pre><code class="language-python">candidates.shape       = [number_of_paths, path_width]
verifier_logits.shape  = [number_of_paths, path_width, vocabulary]
</code></pre>
<p>candidates[:, 0] is the root token already selected by the ordinary LM head. For every later position, the target logit at the previous position predicts the candidate token:</p>
<pre><code class="language-python">target_tokens = verifier_logits[:, :-1].argmax(dim=-1)
matches = candidates[:, 1:] == target_tokens
prefix_matches = matches.int().cumprod(dim=1)
accepted_per_path = prefix_matches.sum(dim=1)
</code></pre>
<p>cumprod enforces the left-to-right rule:</p>
<pre><code class="language-text">raw matches:     [True, False, True, True]
valid prefix:    [1,    0,     0,    0]
accepted length: 1
</code></pre>
<p>The later True values do not count after an earlier rejection.</p>
<p>The reference implementation chooses</p>
<pre><code class="language-python">accept_length = accepted_per_path.max()
best_candidate = accepted_per_path.argmax()
</code></pre>
<p>and appends</p>
<p><code>candidates[best_candidate, :accept_length + 1]</code></p>
<p>The +1 includes the root token.</p>
<p>Define the metrics carefully:</p>
<span class="katex-display"><span class="katex"><span class="katex-mathml"><math xmlns="http://www.w3.org/1998/Math/MathML" display="block"><semantics><mrow><mtext>accepted Medusa tokens</mtext><mo>=</mo><mtext>accept_length</mtext><mo separator="true">,</mo></mrow><annotation encoding="application/x-tex">\text{accepted Medusa tokens}=\text{accept\_length},</annotation></semantics></math></span><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.8889em;vertical-align:-0.1944em;"></span><span class="mord text"><span class="mord">accepted Medusa tokens</span></span><span class="mspace" style="margin-right:0.2778em;"></span><span class="mrel">=</span><span class="mspace" style="margin-right:0.2778em;"></span></span><span class="base"><span class="strut" style="height:1.0044em;vertical-align:-0.31em;"></span><span class="mord text"><span class="mord">accept_length</span></span><span class="mpunct">,</span></span></span></span></span>
<span class="katex-display"><span class="katex"><span class="katex-mathml"><math xmlns="http://www.w3.org/1998/Math/MathML" display="block"><semantics><mrow><mtext>committed tokens</mtext><mo>=</mo><mn>1</mn><mo>+</mo><mtext>accept_length</mtext><mi mathvariant="normal">.</mi></mrow><annotation encoding="application/x-tex">\text{committed tokens}=1+\text{accept\_length}.</annotation></semantics></math></span><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6944em;"></span><span class="mord text"><span class="mord">committed tokens</span></span><span class="mspace" style="margin-right:0.2778em;"></span><span class="mrel">=</span><span class="mspace" style="margin-right:0.2778em;"></span></span><span class="base"><span class="strut" style="height:0.7278em;vertical-align:-0.0833em;"></span><span class="mord">1</span><span class="mspace" style="margin-right:0.2222em;"></span><span class="mbin">+</span><span class="mspace" style="margin-right:0.2222em;"></span></span><span class="base"><span class="strut" style="height:1.0044em;vertical-align:-0.31em;"></span><span class="mord text"><span class="mord">accept_length</span></span><span class="mord">.</span></span></span></span></span>

<p>If all paths accept zero Medusa tokens, the implementation selects path 0 by convention. The choice is harmless because every path shares the same root and only that root is committed.</p>
<p>If several paths tie at a positive greedy prefix length, their accepted token prefix must agree with the same target argmax sequence. Their unaccepted suffixes may differ; choosing the first maximum does not change the committed text.</p>
<h3>Padded paths are not real completions</h3>
<p>The 42 leaves have different depths but are stored at width five. Short paths use a sentinel retrieval index that maps to token ID 0 in the reference code. With the Vicuna tokenizer, ID 0 decodes as <code>&#x3C;unk></code>.</p>
<p>Consequently, a diagnostic trace may say that Medusa proposed <code>&#x3C;unk></code> immediately after an accepted prefix. Sometimes that is not a genuine head proposal--it means the selected leaf ended and the next tensor slot was padding. A correct trace should distinguish</p>
<p>first real candidate mismatch</p>
<p>from</p>
<p>selected path exhausted</p>
<p>rather than interpreting every padded ID as a proposal.</p>
<h2>Part 8: What Is Actually Guaranteed?</h2>
<p>The phrase "Medusa is lossless" needs an acceptance rule attached to it.</p>
<p>Before comparing the rules, separate two operations that are easy to mix up:</p>
<pre><code class="language-text">Medusa-head top-K       decides which tokens enter the candidate tree
target acceptance rule  decides which candidate prefix becomes output
</code></pre>
<p>Every Medusa head produces a distribution over the complete vocabulary. The reference implementation extracts a top-10 pool from each head, then the sparse topology chooses particular rank combinations from those pools. This happens before acceptance. Taking top-K candidates does not imply that typical acceptance is being used.</p>
<h3>Greedy exact verification</h3>
<p>When every accepted Medusa token must equal the target model's greedy argmax, the committed sequence matches ordinary greedy decoding from that same target. Medusa can change the number of tokens committed per step, not their values.</p>
<p>Greedy decoding does not sample. For example, suppose the target distribution at one verified position is:</p>
<pre><code class="language-text">the:   0.35
a:     0.25
its:   0.18
that:  0.12
this:  0.10
</code></pre>
<p>The target token is deterministically <code>the</code>:</p>
<pre><code class="language-python">target_token = probabilities.argmax()  # "the"
accepted = medusa_candidate == target_token
</code></pre>
<p>A Medusa proposal of <code>a</code> is rejected in greedy mode even though the target assigns it probability <span class="katex"><span class="katex-mathml"><math xmlns="http://www.w3.org/1998/Math/MathML"><semantics><mrow><mn>0.25</mn></mrow><annotation encoding="application/x-tex">0.25</annotation></semantics></math></span><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6444em;"></span><span class="mord">0.25</span></span></span></span>.</p>
<p>There is still no guarantee that a speculative token is accepted. The guarantee is:</p>
<blockquote>
<p>at least one target root token is committed per iteration</p>
</blockquote>
<p>not:</p>
<blockquote>
<p>every Medusa head contributes one accepted token</p>
</blockquote>
<h3>Distribution-preserving rejection sampling</h3>
<p>For stochastic decoding, a proper speculative rejection-sampling correction can preserve the target distribution. This uses the draft and target probabilities, not a simple equality test.</p>

<h3>Is typical acceptance deterministic?</h3>
<p>The threshold itself is a deterministic membership test:</p>
<pre><code class="language-python">acceptable = target_probability_of_candidate > threshold
</code></pre>
<p>In the official fast path, all existing tree candidates are tested this way. Medusa selects the path with the longest accepted prefix; if equal-length paths tie, it selects the one with the greatest cumulative target log-likelihood. Given the same logits and tree, this path is deterministic.</p>
<p>A separate sampling variant can remove tokens below the threshold, renormalize the remaining probabilities, and sample one of them. That version is stochastic. Therefore, "typical acceptance" should not automatically be read as "randomly select any token above the threshold."</p>
<p>The first root token is still selected greedily in the official fast path. Typical acceptance can admit more Medusa tokens at nonzero temperature, but it deliberately relaxes exact target-distribution matching. "Similar generation quality" is not the same claim as "identical target distribution."</p>
<p>In every mode, the idea that Medusa has "no target" is incorrect. The same LLM that supplied the hidden state also acts as the verifier during the tree pass.</p>

<h3>Why the loader says the heads were newly initialized</h3>

<h3>Tokens per verification step are not wall-time speedup</h3>
<p>The ratio</p>

<p>For greedy exact mode, compare the complete generated token-ID sequence against ordinary greedy generation from the base target. Text comparison alone can hide tokenizer cleanup differences.</p>
<p>The repository also contains a small educational implementation that trains Medusa-1 heads and performs this exact baseline-ID comparison:</p>

<h2>Common Inference Misreadings</h2>
<table>
<thead>
<tr>
<th>Misreading</th>
<th>Correct interpretation</th>
</tr>
</thead>
<tbody>
<tr>
<td>"Top-K candidate generation is typical acceptance."</td>
<td>Top-K creates the proposal pool. Acceptance is a later target-verification decision.</td>
</tr>
<tr>
<td>"Greedy decoding samples the highest-probability token."</td>
<td>Greedy decoding does not sample; it deterministically takes the argmax.</td>
</tr>
<tr>
<td>"Typical acceptance randomly chooses any token above the threshold."</td>
<td>The official fast path tests existing tree candidates, selects the longest valid prefix, and uses likelihood to break equal-length ties. A sampling variant can be stochastic.</td>
</tr>
<tr>
<td>"Additional length 250 means 250 heads."</td>
<td>It counts flattened candidate-token nodes; a few heads can create hundreds of nodes.</td>
</tr>
<tr>
<td>"Top-K is 10, so every node has ten children."</td>
<td>Ten is the per-head candidate-pool width; the sparse topology retains only selected rank combinations.</td>
</tr>
<tr>
<td>"The tree contains 63 total tokens."</td>
<td>The reference configuration contains 63 non-root choices plus one LM-head root, for 64 verification nodes.</td>
</tr>
<tr>
<td>"There are 64 candidate completions."</td>
<td>There are 64 nodes but 42 root-to-leaf paths in the Vicuna-7B configuration.</td>
</tr>
<tr>
<td>"Because the heads belong to the LLM, their output is automatically accepted."</td>
<td>The original target backbone verifies the tree and can reject every speculative token.</td>
</tr>
<tr>
<td>"At least one Medusa token is guaranteed."</td>
<td>Only the root target token is guaranteed; accepted Medusa tokens may be zero.</td>
</tr>
<tr>
<td>"Typical acceptance is exactly lossless."</td>
<td>Exact greedy matching or proper rejection sampling can preserve target behavior. Typical acceptance deliberately relaxes exact distribution equality.</td>
</tr>
<tr>
<td>"2.156 committed tokens per iteration means 2.156x speedup."</td>
<td>It measures sequence progress per verification call; wall speed also depends on tree-pass latency.</td>
</tr>
</tbody>
</table>
<h2>Part II Summary</h2>
<ul>
<li>Each head produces a full vocabulary distribution; top-K extracts a candidate pool.</li>
<li>A regular Cartesian tree quickly becomes too large, so Medusa uses an offline-optimized sparse rank topology.</li>
<li>Runtime top-K token IDs fill that fixed topology with prompt-dependent values.</li>
<li>Tree attention verifies shared nodes once while preserving the causal ancestry of every path.</li>
<li>Greedy verification accepts only consecutive tokens equal to the target argmax.</li>
<li>Typical acceptance instead allows target-plausible proposals above an entropy-adaptive threshold.</li>
<li>The official fast typical path is a deterministic validation rule; stochastic typical sampling is a separate variant.</li>
<li>One root token is always committed, but zero Medusa tokens may be accepted.</li>
<li>Committed tokens equal one root plus the accepted Medusa prefix.</li>
<li>Acceptance length measures step compression, not wall-clock speedup by itself.</li>
</ul>
<p>The complete mental model is:</p>
<blockquote>
<p>The heads create possibilities. Top-K forms candidate pools. The sparse tree selects combinations worth checking. Tree attention checks them together. The target model and acceptance rule decide which prefix becomes output.</p>
</blockquote>
